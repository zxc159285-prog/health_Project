1. 토큰 인증 및 저장 방식 (Access Token: In-Memory / Refresh Token: DB)
고민했던 선택지:
1안. 기존 세션/쿠키 방식 (Session-based)
2안. 순수 Stateless JWT 방식 (로컬스토리지에만 저장)
3안. Access Token(단기) + Refresh Token(장기 DB 적재) 혼합 방식 (채택)
선택 이유:
세션 방식은 서버를 스케일아웃(확장)할 때 세션 공유(Redis 등) 오버헤드가 크고, 순수 JWT만 쓰면 발급된 토큰이 탈취당했을 때 서버 측에서 강제로 차단/로그아웃시킬 수 없는 치명적 단점이 있습니다.
따라서 짧은 유효기간의 Access Token은 빠르게 서명만 검증하는 Stateless 성능을 누리고, 7일 만료의 Refresh Token은 DB 테이블(h_refresh_token)에 보관하여 탈취 시 즉시 삭제(Revocation)할 수 있는 Stateful 보안 통제권을 확보하기 위해 혼합 방식을 채택했습니다.
2. 파이썬 머신러닝 AI 이탈 예측 모델 (XGBoost + SHAP 분석)
고민했던 선택지:
1안. 딥러닝 인공신경망 (PyTorch / TensorFlow)
2안. 단순 선형 회귀 (Linear Regression)
3안. 트리 기반 XGBoost + SHAP 요인 분석 (채택)
선택 이유:
헬스장 데이터(출석률, 운동시간, 설문점수, 가격 만족도 등)는 표(Tabular) 데이터 구조이므로, 딥러닝보다 트리 기반의 XGBoost가 학습 속도가 빠르고 분류 예측 정밀도가 월등히 뛰어납니다.
또한 사장님에게 단순히 "이탈 위험도 85%"라는 숫자만 제공하면 실제 조치를 취할 수 없으므로, 설명 가능한 AI(XAI) 기술인 SHAP을 이식하여 "가격불만 40%, 방문공백 30%"와 같이 구체적인 이탈 원인 Top 3를 시각화해 혜택 쿠폰 발송 등 비즈니스 조치로 연결되도록 설계했습니다.
3. 실시간 알림 구현 방식 (SSE - Server-Sent Events)
고민했던 선택지:
1안. 주기적 폴링 (Polling - 일정 시간마다 API 재요청)
2안. 양방향 웹소켓 (WebSocket)
3안. SSE (Server-Sent Events 단방향 스트리밍 - 채택)
선택 이유:
알림 서비스는 서버에서 클라이언트로만 메시지를 푸시해 주는 단방향(Server-to-Client) 특성을 가집니다.
웹소켓은 양방향 연결을 위한 핸드셰이크와 소켓 유지 비용이 무겁고, 폴링은 수 초마다 무의미한 DB 쿼리가 발생하는 단점이 있습니다.
반면 SSE는 일반 HTTP 프로토콜 상에서 단방향 이벤트 스트림을 가볍게 연결하고 브라우저 차원의 자동 재연결(Auto-Reconnect)을 기본 지원하므로, 알림 목적에 가장 가볍고 효율적인 SSE 방식을 채택했습니다.
4. B2C 출석 연동 성장형 아바타 (HTML5 Canvas 2D 렌더링)
고민했던 선택지:
1안. 출석수 단계별 GIF/PNG 정적 이미지 교체
2안. Three.js / WebGL 3D 그래픽 엔진
3안. HTML5 Canvas 2D 정밀 레이어링 렌더링 (채택)
선택 이유:
정적 이미지 교체 방식은 출석일수, 바벨 무게, 원판 개수 등 수많은 조합에 맞춰 수십 장의 이미지 리소스를 네트워크로 로딩해야 해서 파일 용량이 급증합니다.
Three.js 3D 엔진은 모바일 브라우저 환경에서 GPU 부담이 커 프레임 드랍이 발생합니다.
따라서 HTML5 Canvas 2D API를 활용해 배경, 아바타, 바벨 원판을 Z-Index 레이어로 직접 코딩 렌더링함으로써 이미지 다운로드 없이 60fps의 매끄러운 반응형 렌더링을 완성했습니다.
5. 프론트엔드 데이터 통신 및 환경 변수 아키텍처 (Native Fetch + .env 단일화)
고민했던 선택지:
1안. Axios 전역 라이브러리 의존성 추가 및 하드코딩 URL
2안. 표준 Native Fetch API + .env 환경 변수 단일화 (채택)
선택 이유:
외부 패키지 설치를 줄여 번들 용량(Bundle Size)을 최적화하고, ES6+ 표준인 fetch API를 공통 유틸화하여 사용했습니다.
또한 소스 코드 내에 API 주소를 하드코딩하지 않고 .env 환경 변수(VITE_BACKEND_URL)를 유일한 진실의 원천(Single Source of Truth)으로 삼아, 개발 환경(localhost)과 테스트 환경(동일 와이파이 네트워크 IP) 간의 서버 전환을 코드 수정 없이 유연하게 처리하도록 채택했습니다.
